# Gotchas already paid for

Traps hit while building this site, oldest first. New ones go at the end with the date: the symptom, the cause and how to avoid it. Search this file for a file name, tool or error message before working in an area. Carried over 2026-11-12 from the claude.ai project's weekly context docs; mentions of "the single-photo section", "Key files" or a week doc point to that archive.

## Through 2026-10-11 (and undated early ones)
- `server-only` throws outside Next's server context (bit three times: seed script, Vitest, Playwright fixtures). Keep pure helpers in non-`server-only` modules (hence `lib/theme-tokens.ts` vs `lib/theme.ts`, `lib/frame-display.ts` vs `lib/frames.ts`, `lib/login-throttle-policy.ts` vs `lib/login-throttle.ts`, `lib/email.ts`, and `lib/password-policy.ts` vs `lib/password.ts`).
- dotenv must load before any module that reads `DATABASE_URL` at import time (hence the lazy `db/client.ts`).
- Deleting `users` without first deleting `sessions` hits `sessions_user_id_users_id_fk`. An `onDelete: "cascade"` on `sessions.userId` was suggested; not applied (schema seen 2026-10-15 has none).
- `lib/password.test.ts` hash tests take ~430–450 ms each — bcrypt cost 12, expected.
- CI wiring typos fixed earlier: stub path, `pull_request`, `chromuim`.
- Stale generated route types: after routes move (e.g. `app/owner` → `app/dashboard/owner`), local `tsc` fails inside `.next/types/validator.ts` (old routes, and a `.next/types` vs `.next/dev/types` `LayoutRoutes` mismatch). CI is unaffected (fresh checkout). Fix: `rm -rf .next && npx next typegen && npx tsc --noEmit` (or `npm run typecheck`). A newly added route (e.g. `/video/[frameNumber]`) isn't in `AppRoutes` until types regenerate, so `PageProps<"/video/[frameNumber]">` errors in the editor until `npm run typecheck` or a running `next dev` regenerates them; then run "TypeScript: Restart TS Server" in VS Code.
- (Anticipated) The root layout reads the DB. Without a cache tag, statically rendered pages would bake in the build-time palette forever; with a `theme`-tagged cache they regenerate on palette change.
- Next 16 cache APIs (pre-migration): one-argument `revalidateTag(tag)` is deprecated (pass a profile or `{ expire: 0 }`), so the `unstable_cache` theme was invalidated with `revalidateTag("theme", { expire: 0 })`.
- Cache Components rules (Next 16.3.4 docs, checked 2026-10-09):
  - Reading `cookies()`/`headers()` outside `<Suspense>` is flagged in dev and fails the build unless the segment sets `export const instant = false`. (Reading `headers()` inside a Server Action, as `loginAction` does, is fine: actions run at request time.)
  - `instant = false` does not clear synchronous IO errors: `new Date()`, `Date.now()`, `Math.random()`, `crypto.randomUUID()` during prerender still fail. Fine after a runtime API or uncached read (request time), or in Server Actions.
  - `redirect()` during render becomes a client-side redirect on a 200 response, not a 307, whether or not it's inside Suspense and even with `instant = false`, because the root-layout shell is always sent first. Real redirects need `proxy.ts` (runs before rendering; Node.js runtime by default in 16; matcher-scoped).
  - `'use cache'` can't call `cookies()`; read outside and pass values in.
  - `cacheLife` can be called in different branches, one per invocation. A cache with `expire` under 5 minutes (only the `seconds` preset) becomes a dynamic hole excluded from prerendering, which would break the root layout's theme read; `minutes` (1 h expire) is safe.
  - `'use cache'` is in-memory per instance (unlike `unstable_cache`, which persisted across deployments/instances). Cold instances re-run the theme query once.
  - `updateTag` works only inside Server Actions (throws elsewhere); `revalidateTag` now needs a profile argument.
  - Routes stay mounted in `<Activity>` across navigations, so form inputs and `useActionState` messages persist when navigating back.
  - `instant = false` on a layout does not cover its child pages; every segment that calls a gate at the top needs its own line (both `account/page.tsx` files were flagged with "uncached data during a navigation" until they got it). A dashboard page that reads only cached data and calls no gate needs none.
- `db/client.ts` uses Neon's HTTP driver (`neon()`). Drizzle's neon-http adapter throws `No transactions support in neon-http driver` on `db.transaction()`. Use `db.batch([...])` (one non-interactive, atomic transaction) or a single upsert, and put conditions in SQL (e.g. `exists (...)`, `case when …`) instead of checking results mid-transaction. `activatePalette` and `seed-palettes.ts` were rewritten to `db.batch` on 2026-10-07; `recordFailure` (2026-10-19) is one `ON CONFLICT DO UPDATE`.
- Cookies are read-only during Server Component render (pages, layouts). `cookies().set/delete` only work in Server Actions and Route Handlers; anywhere else they throw. `getSession` runs in both, so it must never write cookies. It used to delete the cookie on an expired session, which crashed any gated page instead of redirecting (fixed 2026-10-08, regression spec `expired-session.spec.ts`). It rarely fired because the cookie's `expires` equals the row's `expiresAt`; it needs client clock skew or an expiry change.
- Playwright helpers that query the DB from inside a spec run in worker processes, not just global setup, so `.env.test` must be loaded where workers see it (top of `playwright.config.ts`); otherwise `No database connection string was provided to neon()`.
- Under `next start` (`NODE_ENV=production`) the session cookie is `Secure`. Chromium accepts `Secure` cookies on `http://localhost`, so prod e2e works; another browser or a non-localhost test host would need a different approach.
- `reuseExistingServer` makes Playwright test whatever is already on the port instead of starting the configured server. That's why the prod target never reuses and uses its own port (3100).
- dotenv path typo: `config({ path: "env.local" })` (no dot) silently loads nothing → `No database connection string was provided to neon()`.
- (Anticipated) Seeding or editing palettes or frames directly in the DB doesn't clear the Next cache; only `activatePalette` (and future frame actions) do. If old data sticks after seeding, restart dev with `.next/cache` removed, or redeploy.
- (Anticipated) `next build` on Vercel queries Neon for the theme and frames; if that fails, `getTheme()` / the frame queries log and fall back (night-city / no frames) rather than failing the build, cached for `minutes` only.

## 2026-10-12 to 2026-10-18
- A query with `.limit()` and no `.orderBy()` returns rows in whatever order Postgres picks (it was `id` order), so it can also pick the wrong rows. `getHomeFrames` shipped without `orderBy` on the selected row; `home.spec.ts` caught it (2026-10-15). Every list query orders by `displayOrder, id`.
- Playwright's dev target can reuse a `next dev` already on port 3000, and `'use cache'` keeps entries in that server's memory, so stop any running dev server before e2e after seeding or data changes. Editing a cached function's body gives it a new cache key.
- (2026-10-15) Public data pages prerender at `next build`. Under `E2E_TARGET=prod` the frames must already be on the test branch when the build runs, so seeding in Playwright global setup is too late (the webServer build starts first). Seed the test branch once with `npm run seed:frames:test`, like palettes.
- (2026-10-18) Next 16.3's instant-navigation validation flags `params` awaited outside `<Suspense>` on a dynamic route, even with `generateStaticParams` (dev error "encountered runtime data during prerendering"). Public dynamic routes keep a static shell and put the `params` read behind a Suspense boundary (per decision 2026-10-09); `instant = false` stays reserved for gated routes. **Correction 2026-10-22: the Photography detail page never actually had its `params` read behind Suspense; the warning was in the dev log all along without failing anything. Check the dev log, not only the test results, after touching a dynamic route.** **Correction 2026-10-24: `notFound()` inside that boundary does not return a real 404.** Once the read moved behind Suspense, unknown numbers came back 200 on both `next dev` and `next start`: the shell and its 200 status are sent before the streamed part calls `notFound()`. Next still renders the not-found page and adds `<meta name="robots" content="noindex">`. See the `dynamicParams` gotcha (2026-10-24) and the soft-404 decision.
- (2026-10-18) Routes stay mounted (hidden) in `<Activity>` after navigation, so Playwright can click a link on the page being left: wait for the URL/heading of each page before the next click. Client-only behavior (key handlers) exists only after hydration; `waitUntil: "networkidle"` before pressing keys.
- (2026-10-18) A route folder's name is the param name, case included: `[framenumber]` made the route `/photography/[framenumber]`, so `PageProps<"/photography/[frameNumber]">` failed and `params` was `unknown`. macOS file systems ignore case, so rename in two steps (via a temp name; `git mv` only if the files are tracked) and then `rm -rf .next && npm run typecheck`. In zsh, quote paths containing `(public)` or `[...]` (unquoted they are glob patterns).
- (2026-10-18) Vitest strips types without checking them, so a test can pass while `tsc` fails (e.g. `found.next` on a possibly-null result). `npm run typecheck` covers the test files.

## 2026-10-19 to 2026-10-25
- (2026-10-21) **CI never type-checked anything, and never ran a production build.** The workflow's e2e job ran `npm run test:e2e`, the dev target (`next dev`), not `test:e2e:prod`, even though the docs (and the 2026-10-09 decision) said CI ran the production build. `next dev` doesn't type-check, Vitest doesn't either, and no job ran `tsc`, so the `lib/frame-display.test.ts` errors from 2026-10-18 passed CI twice while every local `npm run build` failed on them. Nothing in `next.config.ts` or `tsconfig.json` was involved. Fix (branch `fix-frame-display-types`, merged 2026-10-21): a `typecheck` job that integration waits on, and e2e switched to `test:e2e:prod`. Lessons: check a doc claim about CI against the workflow file; a `[e2e] target:` line in the CI log shows which server ran. Narrow nullable results in tests with Vitest's `assert(value, message)` (an assertion function, so TypeScript narrows) rather than `!` or `?.`; `expect(x).not.toBeNull()` does not narrow.
- (2026-10-21) Consequence of the above: every "e2e on the production build, CI green" claim before 2026-10-21 (Cache Components migration, Photography, single-photo 404, rate limiting) was actually e2e on `next dev`, plus whatever was run locally. CI's first `test:e2e:prod` run (2026-10-21) passed the whole suite, so those features hold on the production build too.
- (2026-10-21) Hand-retyped SQL fragments in Drizzle `sql\`\`` templates fail only at query time, with the full generated SQL in the error: `now() = make_interval(...)` (minus typed as `=`) and `make_intervals` (no such function). Read the "Failed query" text; the integration tests catch these before e2e does.
- (2026-10-21) A loop bound of `limit - 1` in the lockout spec made it submit one wrong password fewer than intended, so the "locks on the 5th" assertion ran on the 4th attempt. By hand it looked fine, because the next attempt was caught by the lock check. The Playwright `error-context.md` page snapshot showed the actual alert text and settled it; check it before suspecting the app.
- (2026-10-21) Every e2e spec logs in from the same address, so they all share one `ip:` throttle counter (limit 20). Global setup clears `login_throttle` on each run. A future spec with many failed logins must keep the suite under 20 failures in one run, or raise `IP_FAILURE_LIMIT` deliberately. (Successful logins don't count.)
- (2026-10-21) Locally there's no `x-forwarded-for`, so `clientIpFrom` returns the dev server's value or `"unknown"`, and every local attempt shares one IP key. On Vercel the platform sets the header. Off Vercel a client can forge it, which only affects the IP key; the email key doesn't depend on it.
- (2026-10-22) `Frame` has no height of its own: the gradient, the image (`fill`) and the caption are all absolutely positioned, so a `Frame` without an aspect class (`aspect-[3/2]`, `aspect-video`) collapses to zero height and its tint disappears, while the `No. NNN` labels can still show and text-based e2e checks still pass. Every `Frame` caller passes an aspect class (including whatever fills the `FrameDetail` media slot; `FrameDetailRoute` passes its `mediaClassName`).
- (2026-10-24) `export const dynamicParams = false` (the usual way to make unlisted params 404 before rendering) fails the build under Cache Components: "Route segment config \"dynamicParams\" is not compatible with `nextConfig.cacheComponents`. Please remove it." So with Cache Components a public dynamic route chooses between a real 404 (read `params` outside Suspense and accept the instant-navigation warning) and a static shell (soft 404: 200 + not-found page + `noindex`). This project picked the soft 404. To check a status by hand: `npm run build && npm run start`, then `curl -sI http://localhost:3000/<path> | head -1` in another terminal. With no server running, `curl -s` prints nothing at all.
- (2026-10-25) **A Playwright `await expect(locator)` with no matcher asserts nothing and always passes.** Both detail specs' `noindex` check had that shape from 2026-10-24 until 2026-10-25, while the docs described it as a real check. When reviewing a spec, check that each `expect(...)` ends in a matcher. Also: on the streamed not-found page Next renders the `noindex` meta tag **twice**, so `toHaveCount(1)` fails; assert `.first().toBeAttached()` (at least one; `toBeVisible` never works on `<meta>`).
- (2026-10-25) An e2e test for an unknown URL on a route that doesn't exist yet passes before the route is built, because Next's ordinary 404 page has the same "This page could not be found." text and `noindex` tag. Expected in TDD; don't read it as the new route working.

## 2026-10-26 to 2026-11-01
- (2026-10-26) **A misspelled `metadata` or `generateMetadata` export (`metaData`, `generateMetaData`) type-checks, builds and passes every test that doesn't read the title; Next just ignores it and the page gets the root layout's default title.** Both Stop motion pages shipped that way until the new tab-title checks caught them. The same goes for `generateStaticParams` (a misspelling silently skips prerendering). Every page spec checks its title.
- (2026-10-30) **The integration cleanup pattern `LIKE '%@example.test'` is case-sensitive**, so a red run that stores an email with capitals or surrounding spaces in the domain (`"  TEST-USER-2@EXAMPLE.TEST "`) leaves rows the cleanup never removes, and they accumulate across runs. Since `users_email_normalized`, such rows can't be inserted at all. Tests that deliberately insert a non-normalized email keep `@example.test` lowercase so a red run is still cleaned up.
- (2026-10-30) Integration failures that look like a concurrency problem (a duplicate key on the first insert of a test, right after the cleanup) can be a plain typo in the test: the "already in use" test inserted `TEST_EMAIL` twice. Read the failing test's setup lines before suspecting other processes.
- (2026-10-30) Commit generated migrations (`db/migrations/*.sql` and `db/migrations/meta/`) with the schema change: `db:migrate` applies only files it can see, and `drizzle-kit generate` diffs the schema against the latest snapshot in `meta/`, so a missing snapshot makes the next `generate` re-emit changes already applied. Never edit or delete a migration that has run anywhere.
- (2026-11-01) A required-check picker (branch protection or ruleset) searches by the check's display name, which is the job's `name:` in the workflow, and lists only checks that ran recently. Use the name shown in the Actions run's job list.
- (2026-11-01) A plain object isn't iterable: `for (… of TEST_ACCOUNTS)` fails to type-check ("must have a '[Symbol.iterator]()' method"); loop over `Object.values(TEST_ACCOUNTS)`. Type the collected insert rows as `(typeof users.$inferInsert)[]` so `db.insert(users).values(rows)` accepts them.
- (2026-11-01) Renaming an e2e account's email drops the old address from the e2e cleanup list, so its row stays on the test branch until the integration suite's `%@example.test` cleanup next runs. Harmless (CI runs integration before e2e), but it explains a stray row. (2026-11-08: a spec that changes an account's email needs the new address in the cleanup list too, hence `changedEmail`.)

## 2026-11-02 to 2026-11-08
- (2026-11-02) Playwright's `getByRole(..., { name, exact: true })` is case-sensitive and matches the whole accessible name, so "Stop Motion" (or a trailing space) fails while "Photography" and "Video" pass. When one item of a list fails with "element(s) not found", compare its label character by character, or read the `error-context.md` snapshot. Without `exact: true`, `getByLabel` is case-insensitive and matches substrings, which is how "New Password" passed for months and why "New password" later matched "Confirm new password" too (strict-mode violation, 2026-11-08).
- (2026-11-02) **A `<form>` without `action` still "works" in the browser**: the button submits a plain GET to the current URL, so nothing is saved and every field lands in the query string (history, server logs). The account settings form shipped that way, and no spec covered it. An e2e check that the URL has no query string after saving catches it.
- (2026-11-04) **Vitest runs test files in parallel by default.** With two integration files creating users and both cleaning `%@example.test` in `beforeEach`, one file deleted the other's rows mid-test: `findUser` returned `undefined`, and a different set of tests failed on each run (the sign of a race, not a bug). Fix: `fileParallelism: false` in the **integration** config. It was first put in `vitest.config.ts`, which is the unit config (`include: ["lib/**/*.test.ts"]`), and had no effect; `npm run test:integration -- --no-file-parallelism` passing proved the diagnosis. Check which config a script loads before editing one. A local run during a CI run on the same test branch causes the same failures.
- (2026-11-04) `useActionState(action, initialState)` takes exactly one action; passing two (`useActionState(updateEmailAction, updatePasswordAction, initialState)`) fails with "No overload matches this call". Each form gets its own hook (and its own pending flag and result message).
- (2026-11-04) `tabRefs.current[key]?.focus;` (no `()`) only reads the method and does nothing; ESLint flags it as `no-unused-expressions`. The e2e "focus follows ArrowLeft" check would fail on it.
- (2026-11-04) Tailwind silently drops unknown classes: `border-acccent-primary` (three c's) left the error message without its red rule, and no test noticed. `grep -rn "acccent" app lib` before a PR touching styles.
- (2026-11-08) With controlled inputs, Playwright typing before hydration is lost (React resets the field and its state stays empty, so a Save button gated on that state stays disabled). Specs that fill controlled forms wait for `networkidle` first, both on `goto` and after redirects to such a page. A click that times out with only "waiting for getByRole('button', { name })" in the log means **no button with that name exists**; a disabled button shows "element is not enabled" instead.
- (2026-11-08) Importing a module into a client component pulls in its imports too: `lib/password.ts` imports Node `crypto` and `bcryptjs`, so even a constant exported from it can't be used by the forms. Shared values the browser needs go in small pure modules (`lib/password-policy.ts`).
- (2026-11-08) `expect(result.success).toEqual({ success: false, reason: … })` compares a boolean to an object and always fails ("expected false to deeply equal …"); compare the whole `result`. `expect(result.success).toBe(false)` passes for *any* failure, so check the reason.

## 2026-11-09 onward
- (2026-11-09) The "at leadt" typo, fixed long ago, came back in `PASSWORD_TOO_SHORT_MESSAGE` when the messages moved into `lib/account-rules.ts`. Moving or retyping user-facing strings can reintroduce old typos; nothing tests the exact wording of that message. (Fixed again 2026-11-11.)
- (2026-11-11) **Deleting the session cookie inside a Server Action makes Next re-render the current page in the action's response**; on a gated page the gate finds no session and redirects to `/login`, so whatever the action returned is never shown. The account lockout's "You've been logged out." message was dropped for that reason (the e2e `error-context.md` snapshot showed the login page, with no tabpanel). To show a message after a logout, it has to live on the page the browser lands on.
- (2026-11-11) `expect(actionResult).toBe({ … })` fails with "serializes to the same string": `toBe` is `Object.is`, and each action call returns a new object. Use `toEqual` for objects; keep `toBe` for strings, numbers and booleans.
- (2026-11-11) A test helper that looks up one thing and rewinds another fails quietly: `rewindLoginThrottleForEmail` briefly gained the account helper's user lookup but still rewound the `email:` key, so the account lock never lifted and the spec failed one step later. When a recovery step fails, check that the rewound key is the one that was locked.
- (2026-11-11) `test:e2e:prod` refuses to start if port 3100 is taken ("http://localhost:3100 is already used … set reuseExistingServer:true"). Usually a `next start` left by an interrupted run: `lsof -i :3100` to see it, `lsof -ti :3100 | xargs kill` to stop it (`kill -9` if it lingers). Don't turn on `reuseExistingServer` for the prod target; it would test an old build.
- (2026-11-11) In the account lockout spec, `page.getByRole("alert")` alone would also match Next's route announcer (it shows up as `- alert: Log in` in the page snapshot); scope alerts to the form (`page.getByRole("tabpanel").getByRole("alert")`).
